# 工作流 SQLite 持久层设计

日期：2026-10-20

## 目标与范围

服务被页面操作、PM2 内存保护或异常退出重启后，保留任务历史、候选结果、人工选择和已接受的排队操作。恢复过程必须先核对外部状态，避免重复修改 Jellyfin 元数据或 qBittorrent 文件名。

第一阶段持久化工作流数据。配置仍使用 config.json，媒体识别游标仍使用 media-cursors.json，登录会话仍在内存中，重启后重新登录。媒体库页面继续实时查询 Jellyfin，不建立另一份媒体目录。媒体库纠错仍只允许手动选择候选；下载完成后的识别范围、刷新等待时间和原有自动识别策略保持现有语义。

## 技术选择与边界

采用单文件 SQLite，数据库固定为配置文件所在目录下的 workflow.sqlite；Docker 默认路径为 /app/data/workflow.sqlite，复用现有数据卷。相较继续扩展 JSON，SQLite 提供事务和分页查询；相较独立数据库服务，不增加部署组件。继续使用单进程、单消费者队列，不支持多个服务实例共同消费同一数据库。

使用 Node 内置 node:sqlite 的 DatabaseSync，不引入 ORM 或第三方原生驱动。最低 Node 版本调整为 22.13.0；该版本开始无需实验开关，但 Node 22 中此模块仍属实验性接口。仅使用基本连接、预编译语句和事务接口，集中封装适配器；项目现有 Node 22 Docker 镜像兼容。

启用 foreign_keys、WAL、synchronous=FULL 和 busy_timeout=5000。数据库放在本地文件系统或本地 Docker 卷中。事务仅包含短数据库操作，不跨网络请求或等待。同步查询限制在分页、单任务及短批次操作内，避免一次反序列化全部历史。

## 组件职责

- 数据库适配器：连接、事务、版本迁移、关闭和数据库错误转换。
- WorkflowRepository：任务、条目、动作的增删查改，以及去重、容量、分页和统计。SQL 不进入控制器或业务服务。
- WorkflowService：调度、识别、人工搜索/确认与业务状态转换。数据库为持久状态来源，内存仅保留当前执行上下文。
- TorrentNamingService：沿用现有命名算法，增加写入意图和回读结果的持久化检查点。

现有 get/list/summary/enqueue/retry/search/confirm 调用边界尽量保留。所有直接修改 job 或 entry 对象的代码必须经过明确保存点；不能只持久化 update(stage) 而遗漏候选、错误和最终结果。

## 数据结构

使用以下三张业务表；数据库结构版本记录在 PRAGMA user_version 中。

| 表 | 主要字段与用途 |
| --- | --- |
| workflow_jobs | id、单调递增顺序、status、stage、created_at、updated_at、source_scope、去重键、item_count、input/result JSON。列表只读取摘要列。 |
| workflow_items | job_id、稳定条目键、顺序、status、phase、payload JSON。保存身份快照、候选及 candidateId、选择结果、选择方式、AI 判断、错误及恢复信息。 |
| workflow_actions | id、job_id、顺序、kind、status、payload JSON、创建/开始/完成时间。保存可序列化操作，替代内存闭包。 |

条目、动作外键关联任务，删除任务时级联删除。建立任务状态/时间、去重键、动作状态/顺序和条目 job_id 索引。JSON 用于已有嵌套业务对象，查询、排序、去重不依赖扫描所有 JSON。

动作类型为 run、search、confirm、retry，保存输入、条目键、候选 ID、scanLibrary 选项和重试快照。候选使用已保存的稳定 ID，重启后不能重新生成再套用旧确认请求。待执行 confirm 在入队时同时固定完整候选快照，后续搜索不能替换其含义。

source_scope 保存规范化的 Jellyfin/qBittorrent 服务地址，不保存凭据。回调去重按 qBittorrent 地址、hash、事件分区，保留现有有效期及显式 recheck 语义。未解决的中断任务也参与去重，返回原任务供处理，避免新回调绕过恢复检查。切换服务地址后历史仍可读；旧动作不得向新地址执行，明确显示来源变更并要求重新发起操作。

## 持久化与执行顺序

1. 接收请求时，在同一事务内检查去重/容量、保存任务和动作，再返回成功响应。保存失败返回错误，不产生仅存在内存中的“已接受”任务。
2. 消费者按持久动作顺序取下一项，在事务内标记执行中；不预加载整条历史队列。
3. 搜索完成、人工候选选择、条目结束、重试准备和任务结束均保存检查点。状态和对应结果在同一事务内更新。
4. 外部写操作前，先提交操作意图；外部请求和回读在事务外执行；回读成功后提交条目结果。已确认成功的条目不再执行写操作。
5. 数据库运行中写入失败时停止派发后续外部修改，记录脱敏日志并将服务置于不可接收写操作状态，等待重启排查；不得继续把后续操作仅保存在内存。

操作意图至少包含目标服务、目标 ID、媒体类型/路径/媒体库、所选 ProviderIds 与预期元数据；重命名包含 torrent hash、文件索引、oldPath 和 newPath。阶段表示 prepared（意图已保存）、verified（外部回读符合预期）、completed（本地收尾已保存）。

## 启动和中断恢复

数据库打开与迁移成功后才启动工作流消费者；先完成旧 running 动作分类，再按顺序恢复 queued 动作。启动核对只读取外部状态，不自动重新发送曾可能执行过的写请求。

| 重启前状态 | 恢复规则 |
| --- | --- |
| queued | 从保存的动作载荷恢复，校验来源和对象身份后顺序执行。 |
| needs_review | 原样保留候选、搜索输入和人工选择，等待用户操作。 |
| completed / failed | 原样保留历史，不自动重跑。 |
| running、尚无外部写入意图 | 标记中断失败，允许用户重试；已完成条目保持完成。 |
| running、存在外部写入意图 | 先回读核对；结果符合则补齐本地收尾，否则标记中断并等待用户处理。 |

中断使用现有 failed 状态并附加 recoveryState=interrupted 和可读原因，避免扩大所有界面的状态枚举。任务同时包含待确认和中断条目时，保留 needs_review 汇总状态，并在条目中显示中断和重试入口。动作失败与条目结果分别记录，不能覆盖先前已完成的结果。

Jellyfin 核对目标的类型、路径、媒体库及预期元数据；仅存在 ProviderIds 不足以证明本次写入成功。核对符合预期且属于自动识别时，幂等补写原游标确认；纠错任务不写游标。游标 JSON 与数据库不能组成跨文件事务，因此采用“数据库意图 → 外部回读 → 游标确认 → 数据库完成”的可重复收尾顺序。

qBittorrent 核对同一 hash 和文件索引：文件名等于 newPath 则补记成功；仍等于 oldPath 则标记可重试；是其他名称、分类变化、索引缺失或目标冲突则停止该条目并提示重新检查。用户重试仍须核对当前状态，不能覆盖外部修改。

网络不可达或核对不充分时保留意图并显示“执行结果待核对”。用户重试必须先再次核对；无法核对则继续失败，不能直接重发。只读搜索可以在用户重试后重做，纠错确认必须保留原人工选择。中断重试按未完成条目恢复，不重新执行整个任务的已完成部分；若扫描尚未生成完整条目集，可重新读取扫描范围，但跳过已完成条目。

这提供持久接收和检查点恢复，不承诺数据库与外部 HTTP 服务之间的严格 exactly-once。

## 查询、容量和清理

任务列表在数据库内按创建顺序倒序分页，并通过聚合查询获取计数；任务详情才加载对应条目和候选。保持现有响应格式，增加的恢复字段为可选字段。前端详情展示中断原因；配置页的重启说明改为任务记录保留、登录会话失效。

沿用 MAX_QUEUE、MAX_JOBS 和 JOB_TTL_MS：完成或失败的终态历史按 TTL/容量清理；queued、running、needs_review，以及带有未解决写入意图的中断任务均受保护。容量检查和新建任务使用同一事务。达到上限仍返回 429，提示处理待确认/中断任务，不再建议通过重启清空记录。去重有效期随任务记录保留期，不额外建立永久去重档案。

历史卸载可减少常驻内存，但单次扫描、单个任务候选、HTTP 缓冲和运行时仍占内存；不以引入 SQLite 保证进程始终小于 256M。现有 PM2 256M 自动重启机制保留。

## 生命周期、升级与故障

关闭时先停止接收和领取新动作，在现有超时内等待当前动作落盘，再关闭连接。超时或强制退出由启动恢复规则处理；页面重启沿用现有繁忙检查，不在本次放宽。配置重新激活时必须先关闭旧消费者，避免两个消费者同时恢复队列。

首次升级创建空数据库；此前仅在内存中的历史和人工候选无法追溯迁移。原配置和游标文件直接沿用，不清空、不改存储格式。数据库迁移按版本在事务内执行，失败回滚；遇到高于程序支持的版本、损坏或无法写入时明确报错，不自动删除数据库或退回内存模式。

备份第一阶段采用停止服务后备份整个 data 目录，恢复时一起恢复数据库、可能存在的 WAL/SHM 文件、配置和游标。运行中禁止只复制 workflow.sqlite。回滚到不支持该结构的版本前应使用升级前备份；旧代码不能读取持久队列。

数据库不保存登录会话、API Key、管理员密码或完整请求头。输入、错误、AI 文本按现有脱敏规则处理。SQLite 文件仍包含媒体名和路径，继承现有 data 目录的访问权限。

## 验收与验证

- Repository：事务回滚、候选稳定 ID、去重分区、FIFO、分页计数、TTL/容量保护、级联删除和迁移失败。
- 生命周期：重建服务后历史与 needs_review 可读，已接受 queued 动作执行一次，已完成动作不再入队，旧登录会话失效。
- 故障注入：分别在意图提交后、HTTP 请求后、回读后、游标确认后强制结束进程，验证恢复核对和补齐收尾。
- 外部状态：以假 Jellyfin/qBittorrent 验证写入成功但响应丢失、目标被修改、无法访问、分类变化、重命名冲突以及来源地址切换，不对真实媒体执行测试写入。
- 功能回归：人工纠错不调用 AI、不自动选择、不修改游标；自动识别原有规则、刷新范围和等待配置不变。
- 运行验证：执行后端测试、前端构建和 UI 冒烟；扩展隔离 PM2 冒烟验证重启后任务保留及队列恢复。Docker 可用时验证数据卷与权限；不可用则明确记录未完成该环境验证。
